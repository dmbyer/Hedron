# Use Case: Ability Invocation & Combat Targeting

**Status:** planned
**Actors:** Player, Mob, System, Administrator
**Module:** `Core/Commands/` (dispatcher fallback — `IAbilityVerbResolver`), `Core/Modules/Abilities/` (new: `IAbilityVerbResolver` impl, `CastCommand`, `AbilityInvocationHandler`, `AbilityBroadcastHandler`, `abilities` verb-discovery extension), `Core/Modules/Combat/` (new: `ICombatSystem.ResolveAbilityStrike`, extracted `MobInRoomResolver`), `Core/ECS/Components/` (reads `CombatStateComponent`)

**Spine:** gameplay-model **S4** — Ability (skills and spells, unified). See [`../design/gameplay-model.md`](../design/gameplay-model.md) Spine B (`AbilityDefinition`, the three `Activation` modes, "skill = run like a command; spell = `cast <name>`", worked examples Kick/Fireball/Haste). **Design lives in the model; this doc is requirements + implementation plan.** This is sub-slice **11-b (invocation & combat targeting)** — the player-facing invocation surface that turns 11-a's substrate into the headline `kick` / `cast <spell>` experience. **11-a (substrate)** ships first (provable via admin `useability`); **11-c (resource-regen + `rest`)** follows.

---

## Description

Turn the 11-a ability substrate into the **player-facing invocation surface**. A player invokes an *Active* **Skill** by typing its name as a bare verb (`kick`, prefix-matched `ki` → `kick`), and an *Active* **Spell** through `cast <spell> [target]`. Both paths converge on the single `IAbilitySystem.Activate(actor, abilityId, target?)` from 11-a — which already checks state, cost, and cooldown and produces effects via `IEffectSystem.Apply`. This slice adds **how a player reaches `Activate`**: dynamic per-actor verb resolution, the `cast` command, state-aware target resolution, combat initiation when an offensive ability opens on a non-combat target, and — the one combat change — routing an offensive ability's **damage** through the existing combat hit/defense math instead of applying it raw.

The headline mechanics:

1. **Dynamic per-ability verb invocation (skills).** Abilities are **per-actor** — you can only invoke what you know — so a learned skill is *not* a global `IVerbRegistry` entry. When the dispatcher's command lookup misses (no exact command, no command-prefix match), it consults a new **`IAbilityVerbResolver`** scoped to the invoking actor: does this player know an *Active* ability whose invocation verb (prefix) matches the typed token? A real command verb always wins; ability resolution is strictly a **fallback** after both command-resolution phases miss.
2. **`cast <spell> [target]` (spells).** One `ICommand` resolves the named spell among the actor's known *Spell*-kind abilities (prefix-matched), takes an optional target, and calls `Activate`.
3. **State-aware targeting.** No target while in combat → the current opponent. Explicit target → resolved in the room (the **3rd** consumer of mob-in-room resolution → extract the deferred `MobInRoomResolver`). Offensive ability on a target not yet in combat → **initiate combat**, the ability being the opening strike. Offensive with no target and not in combat → a friendly error ("Kick whom?"). Self-targeted abilities ignore target args.
4. **Minimal offensive resolution (the only combat change).** An offensive ability's damage resolves against the existing **defense rating** using the existing **combat hit/damage math** via a new `ICombatSystem.ResolveAbilityStrike(attacker, defender, …)` — *not* a raw `IEffectSystem.Apply` of the damage. Non-offensive effects (heals, self-buffs) still apply through `IEffectSystem.Apply` exactly as in 11-a.

This slice **supersedes** the admin `useability` test command with real player invocation (retaining `useability` as an admin-only testing affordance — see Resolved planning inputs). **No** hit/miss/partial distinctions, **no** new ratings, **no** combat command queue, **no** action economy, **no** triggered reactions, **no** AoE/Group/Aspect targeting — all explicitly deferred (named below).

## Postconditions (requirements)

**Dynamic ability-verb resolution (skills) — dispatcher fallback tier**
- A new core seam `IAbilityVerbResolver` (`Core/Commands/`) exposes:
  - `bool TryResolve(uint actorEntityId, string verbToken, out string abilityId)` — returns the **single** *Active* ability the actor knows whose **invocation verb** prefix-matches `verbToken`; ambiguous → `false` (the dispatcher renders a disambiguation line listing the candidates); zero → `false`.
  - `IReadOnlyList<string> GetInvocableVerbs(uint actorEntityId)` — the actor's known *Active* ability verbs (for `abilities` discovery and a future tab-completion seam).
- The **invocation verb** of an ability is, this slice, its `AbilityId` for `Skill`-kind abilities (e.g. `kick`). (`Name`-vs-`Id`-vs-explicit-`InvocationVerb` is a Resolved planning input — `AbilityId` chosen; see Design notes.) **Only `Skill`-kind `Active` abilities are bare-verb-invocable**; `Spell`-kind goes through `cast` and is excluded from `GetInvocableVerbs`/`TryResolve` (so `empower` does not also become a bare verb).
- `IAbilityVerbResolver` is implemented in `Core/Modules/Abilities/` (`AbilityVerbResolver`), reading `AbilitiesComponent.Known` + `IAbilityRegistry`, filtering to `Kind == Skill && Activation == Active`, and prefix-matching against the invocation verb. It is **read-only**: no events, no mutation, no persistence (it is consulted *before* a command body runs).
- **`CommandDispatcher` gains a third resolution phase** (after exact match and `Partial`-prefix resolution, both unchanged): on a command miss, call `IAbilityVerbResolver.TryResolve(context.InvokerEntityId, verb, out abilityId)`. On a unique hit, the dispatcher routes to a single internal **`SkillInvocationCommand`** (a fixed, non-discoverable `ICommand`-shaped initiator) passing the resolved `abilityId` + raw tail; on miss, the existing "Unknown command" path is unchanged. **Command-vs-ability collision policy: a registered command always wins** (ability resolution never runs while a command exact/prefix match exists) — see Design notes for the justification.
- The dispatcher remains the command-initiator runtime (01-layers): consulting a resolver and routing to an initiator is legal initiator-tier orchestration, not domain logic. **No game rule moves into the dispatcher** — it resolves *which* initiator runs; all cost/cooldown/state/targeting decisions stay in the command body and the domain systems.

**`cast` command (spells)**
- `CastCommand` — verb `cast`, alias `c`, `MatchingMode.Partial`, no privilege requirement.
  - Schema: `Token string "spell"` (required, resolved via a new **`KnownSpellResolver : IArgumentResolver`** whose `GetCandidates` returns the actor's known `Spell`-kind `Active` ability ids/names — prefix-matched by the existing parser seam), then `RestOfLine string "target"` (optional).
  - Resolves the spell among the actor's known spells; unknown/unknowable → "You don't know that spell." Resolves the target (below), calls `IAbilitySystem.Activate(actor, spellId, resolvedTarget)`, routes any offensive effect through the combat-strike seam (below), and publishes the events.

**Shared invocation pipeline (both skill verbs and `cast`)**
- Both initiators delegate the *post-`Activate`* work to a shared path so skill and spell invocation never drift. The recommended shape is a small **`AbilityInvocationHandler`** subscribing to `AbilityActivatedEvent` for **broadcast/output only** (room narrative), with the **target resolution + offensive-strike routing performed in the command body** (it is initiator-tier orchestration that must happen *before* `Activate`/strike and feed it). Concretely, per invocation:
  1. **Resolve the ability's effective target** (state-aware, below) → `uint? resolvedTarget`.
  2. **Offensive opens combat** (below) if applicable.
  3. Call `IAbilitySystem.Activate(actor, abilityId, resolvedTarget, ResolveOffensiveExternally: isOffensive)`.
  4. Publish `AbilityActivatedEvent` (and, per the 11-a contract, one `EffectAppliedEvent` per non-combat applied effect).
  5. If the activation succeeded **and** the ability is offensive against a `resolvedTarget`: call `ICombatSystem.ResolveAbilityStrike` (below) with the offensive Power from the activation result, then publish the thin **`AbilityStrikeResolvedEvent`** carrying the strike result. The command publishes **nothing conditional on the strike's outcome** — the narrative `CombatRoundEvent` and the terminal `CombatEndedEvent` (only on `MobDied`/`PlayerIncapacitated`) are published by **`AbilityStrikeHandler`**, because branching on game state to choose which events to fire is handler work, not an initiator's (INV-8).
- "Offensive" is determined by ability data, not the command: an ability is offensive when its `Targeting == Target` **and** it carries a damaging effect (an effect whose target score reduces a defender pool — `HpCurrent`-negative). This classification is read from the registry/effect definitions; **the recommendation is a small helper on the ability/effect read seam** (`IAbilitySystem.IsOffensive(abilityId)` or an `AbilityDefinition.IsOffensive` derived flag) so neither command nor handler hand-rolls effect inspection — see Cross-cutting surfaces (Abilities read seam).

**State-aware target resolution** (performed in the command body, identical for skills and `cast`)
- Resolution order for an ability with `Targeting == Target`:
  1. **Explicit target token present** → resolve an entity in the actor's current room via the extracted `MobInRoomResolver` (below). No match → "You don't see that here."
  2. **No token + actor `IsInState(InCombat)`** → `CombatStateComponent.OpponentEntityId` (the current opponent).
  3. **No token + not in combat + offensive** → friendly error "Kick whom?" (verb-templated). The ability does **not** activate; no cost spent.
- `Targeting == Self` abilities **ignore** any target token entirely (resolved target = the actor); a stray token is not an error.
- **Multi-participant targeting is designed-for but latent.** The command accepts and resolves an explicit target for forward-compat, but combat is 1v1 today, so only the single-opponent path is exercised. `Room`/`Group`/`AspectArea` targeting modes are out of scope (11-a already restricts `Targeting` to `Self | Target`).

**Offensive ability opens combat**
- When an offensive ability resolves to a target the actor is **not** already fighting:
  1. `IEntityStateService.TryEnterState(actorEntityId, InCombat, out failReason)` — on block (e.g. Incapacitated) write `failReason` and abort (no activation, no cost).
  2. `IEntityStateService.TryEnterState(targetEntityId, InCombat, out _)` (mob never rejects; failure is a warn-log no-op, matching `KillCommand`).
  3. `ICombatSystem.StartCombat(actorEntityId, targetEntityId)` (attaches `CombatStateComponent` to both).
  4. Publish `CombatStartedEvent(actor, target, roomId)` — `CombatHandler` renders the standard "You attack X!" opener.
  5. Then proceed with `Activate` + the offensive strike (the ability *is* the opening blow this round; the heartbeat `CombatTickHandler` continues the fight on subsequent ticks).
- When the actor is **already** in combat with the resolved target, steps 1–4 are skipped; the ability fires immediately as an extra strike this tick (gated only by its own cooldown — **no** one-ability-per-round queue this slice; that is the deferred action-economy slice).

**Offensive resolution via combat math (`ICombatSystem.ResolveAbilityStrike`)**
- New method on `ICombatSystem` (domain, `Core/Modules/Combat/Systems/`):
  - `CombatRoundResult ResolveAbilityStrike(uint attackerEntityId, uint defenderEntityId, int basePower)` — computes the strike against the **existing** defense rating (`IStatSystem.GetEffectiveDefense`) using the **existing round-damage computation** (the same `Random.Shared.Next(1, power+2)` style damage and `IAttributeSystem.SetCurrentHp` clamped write `ExecuteRound` already uses), and returns a `CombatRoundResult` (so the strike can yield `MobDied`/`PlayerIncapacitated` outcomes routed through the **same** combat-end path as a normal round). `basePower` is the ability's offensive magnitude — sourced from the effect's computed Power (so a stronger caster hits harder), passed in by the caller; the strike adds the defense mitigation `ExecuteRound` already applies. **No hit/miss roll** (deferred to combat-depth): this slice treats an invoked offensive ability as a landed strike whose *damage* is defense-mitigated, mirroring how `ExecuteRound`'s damage step is reached after the hit check.
  - **Pure**: no events, no persistence (INV-5/INV-8), exactly like `ExecuteRound`. The command publishes the **unconditional** `AbilityStrikeResolvedEvent` carrying the returned `CombatRoundResult`; **`AbilityStrikeHandler`** (a handler — conditional publishing is legal there, INV-8) inspects `Result.Outcome` and routes terminal outcomes (`MobDied`/`PlayerIncapacitated`) through the **existing** `CombatEndedEvent` + handlers (`CombatMobDeathHandler`, slice-10 death path) — **reusing the slice-9/slice-10 death plumbing unchanged**.
- **Seam decision (architectural):** `IAbilitySystem.Activate` stays **effect-agnostic** (11-a unchanged — it applies *all* the ability's effects via `IEffectSystem.Apply`). The **invocation command** is responsible, for an offensive ability, for **substituting** the combat-resolved strike for the raw damage effect: it omits the damaging effect from the `Activate` effect-application set (or `Activate` reports applied effects and the command does not double-apply) and instead calls `ResolveAbilityStrike` with that effect's Power. **Recommended concrete mechanism:** `Activate` gains an opt-out so the **damaging** effect of an offensive ability is *not* auto-applied when the caller will route it through combat — the cleanest expression is `Activate(actor, abilityId, target, ResolveOffensiveExternally: true)` (a flag, defaulting `false` to preserve 11-a/`useability` behavior), causing `Activate` to skip `IEffectSystem.Apply` for the offensive damage effect and instead **return its computed Power** in the result for the caller to feed to `ResolveAbilityStrike`. Non-offensive effects on the same ability (e.g. a self-debuff rider) still apply normally. **This is the surface the spec gate must scrutinize** — see Cross-cutting surfaces → Combat-entry/offensive-resolution and Open question 1 (the flag-vs-split-method fork).

**Terminal-outcome handling (`AbilityStrikeHandler` — the INV-8-clean publish site)**
- A new handler `AbilityStrikeHandler` (Combat module) subscribes to **`AbilityStrikeResolvedEvent`** and owns the *conditional* publishing the command must not do: it publishes `CombatRoundEvent` (so `CombatHandler` renders the hit/damage line identically to a normal round) and, **branching on `Result.Outcome`**, publishes `CombatEndedEvent` on `MobDied`/`PlayerIncapacitated` (reusing `CombatMobDeathHandler` + the slice-10 death path). `DefenderName` is carried point-in-time on the event (captured before any destruction); a handler priority preserves narrative-before-destruction, mirroring combat.md. This is exactly the slice-9 shape (`CombatTickHandler`, a handler, owns the round's conditional `CombatEndedEvent`); the ability strike reuses that boundary rather than smuggling it into the command.
- **`AbilityStrikeResolvedEvent { uint AttackerEntityId, uint DefenderEntityId, uint RoomEntityId, CombatRoundResult Result, string? DefenderName }`** — the one new event type this slice adds: a thin, past-tense fact ("a strike resolved") the command publishes **unconditionally** after `ResolveAbilityStrike`, decoupling the initiator from the terminal branch. Admin `useability` (raw apply, `ResolveOffensiveExternally: false`) publishes **no** strike event, so `AbilityStrikeHandler` never fires for it — no double-apply.

**Output / broadcast (INV-11)**
- `AbilityInvocationHandler` (or `AbilityBroadcastHandler`) subscribes to `AbilityActivatedEvent` (priority 80, notification) for **room narrative**: writes a first-person line to the actor ("You kick the goblin!" / "You invoke empower.") and broadcasts a third-person line ("Alice kicks the goblin!" / "Alice invokes empower.") to other room occupants, via typed messages on `IBroadcastSystem` (mirrors `CombatHandler`). Offensive-strike *damage* narrative rides the **existing** `CombatRoundEvent`/`CombatEndedEvent` output — published by `AbilityStrikeHandler` (above) off the strike's `AbilityStrikeResolvedEvent`, reusing `CombatHandler`'s round narrative — so ability damage reads identically to a normal combat round.
- **Discoverability:** the 11-a `abilities` command is extended so each *Active* `Skill` shows its **invocation verb** (so a player sees `kick` is the thing they type), and each `Spell` shows it is invoked via `cast <name>`. `cast` itself is a normal `Partial` command, so it appears in `help`/`commands` like any verb. Bare skill verbs are **not** added to `help`/`commands` (they are per-actor, not global) — `abilities` is their discovery surface. This is called out as the deliberate discoverability boundary.

**Supersede admin `useability`**
- Player invocation (`kick`, `cast`) is now the primary activation path. `useability` is **retained** as an admin-only (`Full`, `AdminRequirement`) testing affordance — it remains useful for activating an ability the admin character has *not* learned and for exercising `Self`/non-offensive paths deterministically. It keeps its 11-a behavior (always applies effects raw — `ResolveOffensiveExternally` defaults `false`), so it is unaffected by the offensive-strike seam.

**Starting abilities (character creation)**
- `AccountSystem.CreateCharacterAsync` (slice 5) grants each new character a configured starting set: it reads `CharacterDefaultsOptions.StartingAbilities` (a `string[]` of ability ids bound from the existing `CharacterDefaults:` config section, slice 9-d) and calls `IAbilitySystem.Learn(newCharacterEntityId, abilityId)` for each, **before** the **existing** construction-time `SaveEntityAsync` (INV-22 case a — **no new save site**; the granted abilities ride the save the creation flow already performs). Unknown ids are skipped with a warn-log (config-typo tolerance).
- The default set includes **at least one `Skill` and one `Spell`** (e.g. `["kick", "empower"]`) so a fresh character can immediately exercise both a bare skill verb and `cast` — **no admin `teach` required**. The ids are Category-3 balance data; an empty/absent list is valid (a no-ability character).
- This **resolves** 11-a's deferred "none-until-taught" question: the *substrate* stays admin-/learn-driven (11-a unchanged); 11-b adds the **construction-time grant** so player invocation is demoable out of the box.

**Events** (past-tense, thin)
- `AbilityActivatedEvent` (existing, 11-a) — now published by `CastCommand` and `SkillInvocationCommand` (the player initiators) in addition to admin `useability`. Payload unchanged.
- `CombatStartedEvent` (existing, slice 9) — published by the invocation command when an offensive ability opens combat. Payload unchanged.
- **`AbilityStrikeResolvedEvent` (new, thin)** — published **unconditionally** by the invocation command after `ResolveAbilityStrike`; carries the strike `CombatRoundResult` + point-in-time `DefenderName`. Consumed by `AbilityStrikeHandler`.
- `CombatRoundEvent` (existing, slice 9) — published by **`AbilityStrikeHandler`** off `AbilityStrikeResolvedEvent`, so the strike's damage narrative reuses `CombatHandler`. Payload unchanged.
- `CombatEndedEvent` (existing, slice 9) — published by **`AbilityStrikeHandler`** when the strike `Result.Outcome` is `MobDied`/`PlayerIncapacitated`, reusing the existing combat-end handlers. Payload unchanged.
- `EffectAppliedEvent` (existing) — published per non-combat applied effect, per the 11-a contract.
- **One new event type** (`AbilityStrikeResolvedEvent`); every other reaction reuses an event from 11-a or slice 9. The new event exists solely to move the strike's *conditional* terminal publishing out of the initiator and into `AbilityStrikeHandler` (INV-8).

## Main flow

### Flow 1 — Invoke a skill by bare verb (self-target / non-offensive omitted; this is the offensive-in-combat case)
1. Player (already fighting a goblin) types `kick` (or `ki`). `CommandDispatcher` misses exact + `Partial`-prefix command lookup, then calls `IAbilityVerbResolver.TryResolve(playerId, "kick")` → unique hit `kick` → routes to `SkillInvocationCommand("kick", tail="")`.
2. The command resolves the target: no token + `IsInState(InCombat)` → `CombatStateComponent.OpponentEntityId` (the goblin). Actor is already fighting it, so no `StartCombat`.
3. Calls `IAbilitySystem.Activate(playerId, "kick", goblinId, ResolveOffensiveExternally: true)` — 11-a checks known/state/cooldown/cost, spends Stamina, sets cooldown, **skips** applying the damage effect, returns `Outcome=Activated` + the computed offensive Power.
4. Command calls `ICombatSystem.ResolveAbilityStrike(playerId, goblinId, power)` → defense-mitigated damage applied via `SetCurrentHp`; returns `CombatRoundResult`.
5. Command publishes `AbilityActivatedEvent` (narrative) + the unconditional `AbilityStrikeResolvedEvent` (the strike result). `AbilityInvocationHandler` writes "You kick the goblin!" / room broadcast.
6. `AbilityStrikeHandler` (on `AbilityStrikeResolvedEvent`) publishes `CombatRoundEvent` — `CombatHandler` renders the hit/damage line — and, **only if** `Result.Outcome` is `MobDied`/`PlayerIncapacitated`, publishes `CombatEndedEvent`, reusing `CombatMobDeathHandler` (mob destroy + slot free) or the slice-10 death path. The command itself published nothing conditional (INV-8). Cooldown gates re-invoking `kick` until the heartbeat decrements it.

### Flow 2 — `cast <spell>` a self-buff (non-offensive)
1. Player types `cast empower` (or `c emp`). `CastCommand` runs. `KnownSpellResolver` resolves `empower` among the actor's known `Spell` abilities.
2. `empower` is `Targeting == Self` → target token ignored, resolved target = the actor. Not offensive → no combat entry, no strike.
3. Calls `IAbilitySystem.Activate(playerId, "empower", null)` (default `ResolveOffensiveExternally: false`) — spends Mana, sets cooldown, applies the `Timed StatModifier(+Body)` via `IEffectSystem.Apply`.
4. `CastCommand` publishes `AbilityActivatedEvent` + one `EffectAppliedEvent` for the buff. `AbilityInvocationHandler` writes "You invoke empower." / room broadcast.

### Flow 3 — `cast <spell> <target>` offensive, target not yet in combat (opens combat)
1. Player (not in combat) types `cast firebolt goblin`. `CastCommand` resolves `firebolt` (a `Spell`, `Targeting == Target`, offensive). Explicit token `goblin` → `MobInRoomResolver` resolves the goblin in the room.
2. Offensive + not already fighting it → `TryEnterState(player, InCombat)` (ok), `TryEnterState(goblin, InCombat)`, `ICombatSystem.StartCombat(player, goblin)`, publish `CombatStartedEvent` → `CombatHandler` renders the opener.
3. Calls `Activate(player, "firebolt", goblin, ResolveOffensiveExternally: true)` — spends Mana, sets cooldown, skips the raw damage effect, returns its Power.
4. Command calls `ResolveAbilityStrike(player, goblin, power)` → defense-mitigated damage; publishes `AbilityActivatedEvent` + `AbilityStrikeResolvedEvent`. `AbilityStrikeHandler` publishes `CombatRoundEvent` (and `CombatEndedEvent` only if the strike is terminal). Subsequent heartbeat ticks continue the fight via `CombatTickHandler`.

### Flow 4 — Offensive ability, no target, not in combat (friendly error)
1. Player (not in combat) types `kick`. Dispatcher resolves it to `SkillInvocationCommand("kick")`.
2. Target resolution: no token, not in combat, `kick` is offensive → command writes "Kick whom?" and returns. **`Activate` is never called**; no Stamina spent, no cooldown set.

### Flow 5 — Command-vs-ability collision (a real command wins)
1. A player who knows a skill named `look` (hypothetical) types `look`. `CommandDispatcher` resolves `look` as the **registered `LookCommand`** at the exact-match phase — `IAbilityVerbResolver` is never consulted. The skill is unreachable as a bare verb; the player must use it via any future explicit-invoke path (out of scope) — the room-look command wins, by policy. (No starter skill collides with a real verb; this is the guaranteed precedence, not a live conflict.)

`IAbilitySystem`, `ICombatSystem`, `IStatSystem`, `IAbilityVerbResolver`, `KnownSpellResolver`, `MobInRoomResolver`, and `IEffectSystem` **never publish** (INV-5). The command initiators publish only **unconditional** facts (`AbilityActivatedEvent`, `CombatStartedEvent` on the distinct offensive-opens-combat path, `AbilityStrikeResolvedEvent`); the *conditional* terminal events (`CombatRoundEvent`, `CombatEndedEvent`) are published by `AbilityStrikeHandler` (a handler — INV-8). **One new event type** (`AbilityStrikeResolvedEvent`) is introduced.

- **No new gameplay state.** This slice adds **no** new component and **no** new persistent state — it is pure invocation/orchestration over 11-a's `AbilitiesComponent` and slice-9 combat state. The authoring + inspection surfaces for ability state already shipped in 11-a (`teach` authors known abilities; `abilities` inspects them); this slice **extends** `abilities` to surface the *invocation verb* so a player can discover what to type. That extension is the INV-18 obligation for the one player-facing affordance this slice adds (a learned skill becoming typeable), and it ships in the same slice (WP-3).

## Cross-cutting surfaces stressed

- **Commands — Gap exposed → resolved in-slice (framework lands with the slice).** Dynamic **per-actor verb invocation** is a genuinely new resolution surface the command framework does not have today: a learned skill becomes a typeable verb that is *not* a global `IVerbRegistry` entry (it depends on *who* is typing). Hand-rolling this — e.g. each ability registering a global command, or `cast` string-switching on ability ids — would be the slice-2-style miss. Per ground rule 9 the supporting framework lands **in this slice**: a core `IAbilityVerbResolver` consulted at a **new third dispatcher resolution phase** (after exact + `Partial`-prefix, both unchanged), routing to a single internal `SkillInvocationCommand`. This is reused-by-design (a future "invoke any registered actor-scoped action" — emotes-you-know, social verbs — folds through the same resolver phase), so it is not a one-off. The collision policy (registered command always wins) is structural: the ability phase only runs after both command phases miss. **This is one of the two surfaces the spec gate must scrutinize** (the other is offensive resolution). `cast` itself is an ordinary `Partial` command and rides the existing framework unchanged; its spell argument rides the existing `IArgumentResolver`/`GetCandidates` seam (the same one `ItemInRoomResolver` uses) — **Adequate** for that part.
- **Combat-entry / offensive resolution — Gap exposed → resolved in-slice (framework lands with the slice).** Routing an offensive ability's damage through combat mitigation rather than `IEffectSystem.Apply` requires a seam that does not exist: 11-a's `Activate` applies *every* effect raw. The clean resolution is a new **`ICombatSystem.ResolveAbilityStrike`** (reusing `ExecuteRound`'s existing defense/damage math via a shared private helper) **plus** an opt-out on `Activate` so the offensive damage effect is not double-applied. The rejected hand-rolls — (a) letting the ability `Apply` raw damage (bypasses defense, double-counts, diverges from combat), or (b) duplicating defense math in the command (INV-8 violation; rule must live in `ICombatSystem`) — are both called out so the gate sees the seam was chosen, not missed. The two viable shapes for the opt-out (a flag on `Activate` vs. a dedicated split method) are surfaced as **Open question 1**; the planner recommends the flag for minimal 11-a churn. **The spec gate must confirm `Activate` stays effect-agnostic in spirit (the flag only *gates* one effect's application; it adds no combat knowledge to `IAbilitySystem`) and that damage mitigation stays entirely in `ICombatSystem`.** The strike's *conditional* terminal publishing (`CombatRoundEvent`, and `CombatEndedEvent` on a kill) lives in the new `AbilityStrikeHandler` (a handler), not the command — so the initiator publishes only unconditional facts (INV-8).
- **Output — Adequate.** Ability narrative rides typed messages on `IBroadcastSystem`/`IOutputWriter` (INV-11), mirroring `CombatHandler`'s first-/third-person fan-out. Offensive-strike *damage* narrative **reuses** the existing `CombatRoundEvent`/`CombatHandler` path verbatim — ability damage reads exactly like a combat round. No new output infrastructure.
- **Event bus — Adequate (one new thin event).** The slice adds a single new event, **`AbilityStrikeResolvedEvent`** — published unconditionally by the command after a strike and consumed by `AbilityStrikeHandler`, whose sole job is the *conditional* terminal publishing (`CombatRoundEvent`, and `CombatEndedEvent` on a kill) the initiator must not do (INV-8). Every other event is existing 11-a/slice-9 (`AbilityActivatedEvent`, `EffectAppliedEvent`, `CombatStartedEvent`, `CombatRoundEvent`, `CombatEndedEvent`), published from initiators/handlers (INV-5/INV-6). Reusing `CombatEndedEvent` means the slice-10 death path and `CombatMobDeathHandler` handle ability-kills with zero new wiring.
- **ECS queries — Adequate.** `AbilityVerbResolver`/`KnownSpellResolver` read `AbilitiesComponent` via `EntityService.TryGet`; `MobInRoomResolver` iterates `MobDataComponent` + `LocationComponent` exactly as `TryFindTargetInRoom` does today. No `is`/`as` (INV-4).
- **Persistence — Adequate (no change).** **Persistence opt-in audit:**
  - **Level 1 (entity domain):** This slice's runtime path introduces **no new entity construction path** and **no `PersistentEntity` change**. It reads players (persistent domain, already opted in) and mobs (world-content domain, never opted in, INV-23) and mutates only **transient** state (HP via `SetCurrentHp`, cooldowns set by 11-a's `Activate`, `CombatStateComponent` via slice 9). No entity transitions domains. The one construction touch — the **starting-abilities grant** (WP-4) — does not create an entity or change a domain; it adds `Learn` calls to slice 5's *existing* character-construction path (the new character already carries `PersistentEntity`).
  - **Level 2 (component inclusion):** This slice introduces **no component**. It reads `AbilitiesComponent` (11-a; `[Persistent]`, `Known` only via converter — correct, unchanged) and reads/writes `CombatStateComponent` (slice 9; **not** `[Persistent]` — transient combat state, correct, unchanged) and `PoolsComponent.CurrentHp` (slice 8a; `[Persistent]`, covered by periodic flush). No `[Persistent]` status is added, changed, or relied-upon incorrectly.
  - **Level 3 (save-on-change scope):** **No *new* `SaveEntityAsync` site is added.** All state the runtime invocation path mutates (HP, cooldown, combat state) is transient/flush-covered, exactly like ordinary combat rounds (combat.md: "save-on-change is not used for combat HP"); the invocation commands are **not** admin boundary saves and **not** session-end saves and must not persist (any `SaveEntityAsync` in an invocation command would violate INV-22). The **only** persistence touch is the starting-abilities grant (WP-4), which rides slice 5's **existing** construction-time save (INV-22 case a — a pre-existing, legitimate save site, not a new one).
- **Time / heartbeat — Adequate (no change).** Cooldown decrement (11-a's `AbilityCooldownTickHandler`) and round continuation (slice 9's `CombatTickHandler`) already run on the heartbeat; this slice adds **no** new tick subscriber. An invoked combat ability fires immediately (gated by its own cooldown), and the heartbeat continues the fight — **no** action-economy metering this slice (deferred).
- **Sessions — Adequate.** `cast`/skill targeting resolves entities in the actor's room via `LocationComponent` + the resolver; no `ISessionManager` name-resolution is needed for targets (mobs are not sessions). The resolver context (`CommandArgumentResolverContext`) already carries `InvokerEntityId` + `IServiceProvider`, sufficient for room lookup.
- **Configuration — Adequate (one new key).** A new `CharacterDefaults:StartingAbilities` list (a `string[]` on the existing `CharacterDefaultsOptions`, slice 9-d) binds via the existing `IConfiguration` host — no new config *infrastructure*, the same pattern 9-d uses for starting attributes/pools. Ability cost/cooldown numbers remain 11-a's Category-3 registry data; the offensive strike reuses combat's existing damage formula (no new tunable).
- **Modules — Adequate.** New initiators/handlers/resolvers register in the existing `AbilitiesModule` (`AddAbilitiesModule`) and `CombatModule`; the dispatcher change is in `Core/Commands/`. No new module.

## Design notes

- **Dynamic verb resolution is dispatcher-tier (legal), not domain logic.** 01-layers names the `CommandDispatcher` as the runtime of the command-initiator tier. Consulting `IAbilityVerbResolver` to decide *which initiator* runs is initiator-tier orchestration — the same category as exact/prefix command resolution. **No game rule enters the dispatcher**: the resolver is a read-only known-abilities lookup; all cost/cooldown/state/targeting decisions remain in the command body and `IAbilitySystem`/`ICombatSystem`. The resolver is a **core** seam (`Core/Commands/`) implemented by the **Abilities** module (the dependency arrow points the legal way: dispatcher → core interface ← Abilities domain), mirroring the `IEffectContributor` shape 11-a canonized (INV-24) and the `IArgumentResolver`/`IAuthorizationChecker` DI-collected-seam precedent.
- **Command-vs-ability collision: the command wins, structurally.** The ability phase runs **only after** both command resolution phases (exact, then `Partial`-prefix) miss — so a registered verb can never be shadowed by a learned ability. Rationale: commands are the stable, global, discoverable surface; a player's learned-ability set is dynamic and per-actor; letting an ability shadow a core verb (`look`, `kill`) would make the same keystroke mean different things to different players and could mask a critical verb. No starter ability collides with a real command, so this is a guaranteed precedence, not a live conflict. (If a designer ever *wants* a skill to override a verb, that is a deliberate future feature with its own gate, not a default.)
- **Invocation verb = `AbilityId` (this slice).** Skills are invoked by their id (`kick`); the model says "a skill executes like a command." Keeping the verb identical to the id avoids authoring a parallel verb field before any consumer needs the distinction. The seam is forward-compatible: an additive `AbilityDefinition.InvocationVerb` (defaulting to the id) drops in later for ids that should not be the literal verb — `GetInvocableVerbs`/`TryResolve` would read that field instead. Flagged as the explicit deferral.
- **The offensive-strike seam keeps `Activate` effect-agnostic in spirit.** 11-a's invariant is "abilities produce effects; the effect system computes Power; the ability system never computes damage/mitigation." This slice preserves that: `Activate` still does not compute mitigation — it merely **gates** whether one effect (the offensive damage) is applied internally, and surfaces that effect's already-computed Power for the caller to hand to `ICombatSystem`. Damage mitigation lives **only** in `ICombatSystem.ResolveAbilityStrike` (reusing `ExecuteRound`'s math). This is the minimal clean seam: the alternative of a separate `ApplyNonDamageEffects` + `GetOffensivePower` pair is functionally identical but adds surface; the flag is recommended (Open question 1) for the smallest 11-a delta. The spec gate should verify no defense/damage arithmetic leaks into `IAbilitySystem` or the command body. Symmetrically, the strike's terminal-outcome publishing lives in `AbilityStrikeHandler` (a handler), never the command — the initiator publishes only the unconditional `AbilityStrikeResolvedEvent` (INV-8).
- **No hit/miss this slice — a strike is a defense-mitigated landed blow.** `ResolveAbilityStrike` reaches the damage step `ExecuteRound` reaches *after* its hit check; this slice does not roll to-hit for abilities. Distinct offensive/defensive ratings, a to-hit roll for abilities, and triggered dodge/parry are the **combat-depth** use-case. Calling this out so the gate does not read the missing roll as an oversight.
- **No action economy this slice — immediate, cooldown-gated.** An invoked combat ability fires the instant it is typed (subject only to its 11-a cooldown); the heartbeat-driven round continues the auto-attack. One-ability-per-round, immediate-first-then-metered, cooldown-blocks-queue, and Action Points are the **combat action-economy** use-case. The `ResolveAbilityStrike` + `CombatRoundEvent` shape is forward-compatible: the action-economy slice schedules *when* the strike resolves; the resolution call itself is unchanged.
- **`MobInRoomResolver` discharges combat.md's deferred extraction (INV-19, 2nd–3rd consumer).** `kill` is the prior mob-in-room consumer; ability targeting is the next. The resolver lifts the prefix-match out of `TryFindTargetInRoom`; `KillCommand` either keeps `TryFindTargetInRoom` (now delegating to the resolver) or moves to the resolver — **its behavior must not change**. The extraction is justified by the new player-facing targeting surface regardless of whether the count is judged 2 or 3 (INV-19 also fires on a new player-facing surface, not only the ≥3-use rule).
- **`useability` retained for admin testing.** It remains the deterministic way to activate an ability the admin has not learned and to exercise `Self`/non-offensive paths without combat. It keeps `ResolveOffensiveExternally: false` (applies all effects raw), so it is orthogonal to the offensive-strike seam and needs no change beyond existing in parallel with the new player verbs.
- **Latent multi-participant targeting.** The command accepts an explicit target so the *shape* supports future N-participant combat, but combat is 1v1, so only the single-opponent path is exercised. `Room`/`Group`/`AspectArea` modes are out of scope (11-a already caps `Targeting` at `Self | Target`).
- **On ship:** fold the invocation pipeline into `architecture/subsystems/abilities.md` (authored when 11-a ships) and the dispatcher third-phase into `architecture/subsystems/commands.md`; trim this doc to the durable behavior spec (docs lifecycle; INV-D2).

## Resolved planning inputs

Decisions the planner ratified for execution (architectural choices made and justified; **product** decisions surfaced as Open questions, not guessed):

1. **Offensive-resolution seam.** `Activate` stays effect-agnostic; the **invocation command** routes offensive damage through a new `ICombatSystem.ResolveAbilityStrike` (with the `ResolveOffensiveExternally` flag, default `false`, so the damage effect is not double-applied), then publishes the **unconditional** `AbilityStrikeResolvedEvent`. The strike's *conditional* terminal publishing (`CombatRoundEvent` + `CombatEndedEvent` on a kill) lives in the new **`AbilityStrikeHandler`** (a handler), never the command — the slice-9-parallel boundary (INV-8). Non-offensive effects still apply via `IEffectSystem.Apply`; damage mitigation lives only in `ICombatSystem`. (The flag-vs-split-method shape was Open question 1; the spec gate cleared the flag.)
2. **Dynamic verb resolution.** A core `IAbilityVerbResolver` consulted at a **new third dispatcher resolution phase** (after exact + `Partial`-prefix), routing to an internal `SkillInvocationCommand`. **Registered commands always win.** Skills are bare-verb-invocable; spells go through `cast`.
3. **Invocation verb = `AbilityId`** for skills this slice (additive `InvocationVerb` field deferred until a consumer needs id≠verb).
4. **`MobInRoomResolver` extracted** as the INV-19 3rd consumer; `KillCommand` behavior unchanged.
5. **`useability` retained** as an admin-only testing affordance (not removed).
6. **No new persistent state, no `SaveEntityAsync`** — all mutated state is transient/flush-covered (INV-22 no-save slice).
7. **Out of scope (designed-for-the-seam, not implemented):** combat command queue / action economy (→ combat action-economy use-case); hit/miss/partial, distinct ratings, speed-scaled actions, Action Points (→ combat-depth); triggered reactions (→ combat-depth); AoE/Group/AspectArea targeting + aspect resolution + multi-participant combat (latent).
8. **Acknowledged debt — in-combat double action.** Until the combat action-economy slice, an actor already fighting who invokes an offensive ability gets that strike **plus** the heartbeat auto-attack in the same ~2s tick (no one-ability-per-round metering). Intentional and bounded; tracked as a backlog item (combat action-economy) — not fixed here (the "minimal combat touch" boundary for 11-b). INV-19 acknowledged-debt entry.

## Open questions

Surface to the owner before implementation; the cross-cutting **Gap exposed** items above are open questions by default.

1. **(Architectural — recommend, confirm) Offensive opt-out shape on `Activate`.** A `ResolveOffensiveExternally` **flag** on `Activate` (default `false`, recommended — smallest 11-a delta) vs. a dedicated **split method** (e.g. `ActivateNonDamage` + a `GetOffensivePower` query) so `Activate`'s signature never grows a combat-flavored parameter. Both keep mitigation in `ICombatSystem`; the planner prefers the flag. *Potentially blocking* — it determines the WP-1 `IAbilitySystem` delta and is the exact seam the spec gate scrutinizes. Owner to confirm the flag (or pick the split).
2. **(Resolved — owner-confirmed) Starting-ability-set acquisition.** **Decision: (a)** — a `CharacterDefaults:StartingAbilities` config list granted at character creation in `AccountSystem.CreateCharacterAsync` (construction-time, riding the existing INV-22 case-a save), so a fresh character can invoke `kick`/`cast empower` with **no admin `teach`**. The owner's explicit call: do **not** make admin-granting a prerequisite for a playable character. Default set includes ≥1 Skill + ≥1 Spell. See Postconditions → *Starting abilities* and **WP-4**.
3. **(Product) Bare-verb discoverability depth.** `abilities` will list each skill's invocation verb (decided). Should a learned skill *also* appear in `help`/`commands` somehow (e.g. a synthetic "Abilities" category listing the actor's invocable verbs), or is `abilities` the sole discovery surface (recommended — keeps the global command index stable and per-actor verbs out of it)? *Non-blocking; recommend `abilities`-only.*
4. **(Product) Offensive-ability narrative voice.** Should the ability line ("Alice kicks the goblin!") and the strike damage line ("Your kick hits the goblin for 7!") be **two** messages (ability narrative via `AbilityInvocationHandler` + damage via `CombatHandler`'s round narrative, recommended — reuses combat output verbatim) or **one** fused line? Two is the lower-effort, consistent-with-combat default. *Non-blocking; recommend two.*
