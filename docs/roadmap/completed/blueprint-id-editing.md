# Blueprint id editing — rename + choose-at-creation (completed)

> Implemented on branch `claude/blueprint-id-editing-ceea08`, 2026-07-20. Living docs: [`admin-authoring`](../../features/admin-authoring/admin-authoring.md), [`content-tooling`](../../features/admin-authoring/content-tooling.md), [`content-authoring`](../../features/admin-authoring/content-authoring.md).

## Outcome

Authored world content is no longer stuck with the generated `*.adhoc.*` blueprint id it was minted with. The offline Blazor content editor gained two new authoring paths, both fully backed by `IContentDefinitionCatalog`: **choose-at-creation** (a deliberate id typed on the New form, falling back to an adhoc id when left blank) and **rename** (an existing definition's blueprint id changes, cascading `oldId → newId` through every YAML reference across the content graph). Rename is the structural sibling of the existing `DeleteAsync` cascade — same reference-index traversal, generalized so a referring field is *rewritten* rather than *cleared*. The slice also closed a pre-existing gap: `RoomTemplate.SpawnRules[].BlueprintId → Mob/Item` was not a declared reference edge, so deleting a mob/item left dangling spawn-rule entries invisible to the integrity sweep; it is now a first-class two-kind edge feeding rename, delete, and the sweep uniformly. YAML-only, offline (INV-22/23) — the live world adopts renamed ids on the next `reload`.

## Behavior digest

**Preconditions:** the offline Blazor editor running against the loopback `Hedron.Web` host; the content directory writable; for rename, the target definition file for `oldId` exists on disk; for create-with-id, the author entered a deliberate id on the New form (blank falls back to adhoc).

**Postconditions (as specified):**
1. Rename writes a `newId` file carrying the definition's full state and deletes the `oldId` file (no orphan).
2. Rename rewrites every external referrer across all six declared edges (`Room.AreaId`, `Room.Exits[dir]`, `Item/Mob.SpawnRoomBlueprintId`, `Area.Rooms[]`, `Room.SpawnRules[].BlueprintId → Mob/Item`).
3. A self-referential field on the renamed definition itself (e.g. a self-loop exit) points at `newId` in the new file, not `oldId`.
4. Rename refuses — no write, `oldId` file intact, structured errors — when `newId` is malformed (empty, path separator, `..`, illegal char) or already taken by a same-kind definition (collision → refuse, no merge).
5. A kind-prefix mismatch on `newId` is a non-blocking warning, not a refusal.
6. Renaming a room warns about out-of-YAML re-keying (persistent player/item `LocationComponent.RoomBlueprintId`, and specifically `World:StartingRoomBlueprintId` when it matches) without ever writing to SQLite or `appsettings.json`.
7. `Referrers(Mob, X)` / `Referrers(Item, Y)` resolve `Room.SpawnRules[]` entries against either kind; `SweepBroken`/`BrokenFor` flag a spawn-rule id only when it resolves as **neither** — closing the false-negative gap that let delete leave dangling spawn-rule entries.
8. Delete now also removes matching `Room.SpawnRules` entries when the referenced mob/item is deleted (the edge fix applies to delete uniformly).
9. A definition created with a deliberate id carries that id on disk; the create write refuses a malformed or already-taken id (same validation as rename).
10. No event is published; no `EntityService`/SQLite is touched; a mid-cascade referrer failure does not throw (best-effort, matching `DeleteAsync`).

**Main flow (rename):** author invokes Rename on an editor page → `IContentDefinitionCatalog.RenameAsync(kind, oldId, newId)` → `IContentValidator.ValidateBlueprintId` (format errors refuse; kind-prefix mismatch defers a warning) → uniqueness check via `IContentReferenceIndex.Resolves` + `Load(oldId)` (collision or missing target refuses) → a fresh template is constructed with `BlueprintId = newId`, state copied, self-references rewritten, written via the matching writer → `Referrers(kind, oldId)` queried (excluding the target's own self-reference) and each external referrer rewritten `oldId → newId` via the generalized `TryApplyCascadeAsync` (best-effort) → old file deleted → out-of-YAML advisories folded into `Warnings` → `ContentRenameResult` returned. **Create-with-id:** the New form's id field (or an explicit-id `CreateNew` overload) flows into `CreateAsync`, which runs the same `ValidateBlueprintId` + uniqueness guard before the first write.

## Decisions

- **Rename is delete's sibling; the verb belongs with the data it mutates.** `RenameAsync` lands on `IContentDefinitionCatalog` — the system that already owns YAML read/write and the delete cascade — reusing `IContentReferenceIndex.Referrers`. Putting it in a command, the loader, or the UI would be a layering inversion (INV-1/INV-2).
- **Cascade generalizes over the write value, not a new traversal.** `TryCascadeClearAsync` (delete) and the new rename-rewrite path are the same walk with a different terminal action — clear is rewrite-to-empty, rename is rewrite-to-`newId`. One `TryApplyCascadeAsync(referrer, oldId, string? newId)` serves both (`null` = clear), meeting the ≥3-consumer bar for a shared seam (INV-19) rather than a parallel cascade implementation.
- **The spawn-rule reference edge was declared now, closing a pre-existing SR-2 gap.** `RoomTemplate.SpawnRules[].BlueprintId` is a real reference to the mob/item `SpawnSystem` spawns, but was absent from `ContentReferenceIndex.DeclaredEdges` — so deleting a mob left rooms that spawned it untouched, invisible to the integrity sweep. `EdgeDeclaration.TargetKind` generalized to `TargetKinds` (a spawn-rule id carries no kind discriminator, so it resolves against *either* mob or item) fixes rename, delete-cascade, and the sweep uniformly with a one-line data addition. Bounded over-match accepted: if a mob file and an item file happen to share an id, deleting one removes the room's spawn-rule entry that may have meant the other — pre-existing property of `SpawnRule`, harmless for rename (pure id-equality rewrite), bounded by the single-author offline scope.
- **Template ids are immutable, so rename rebuilds rather than mutates.** Every `*Template.BlueprintId` is get-only/constructor-set (it *is* the file name). `CloneWithNewId` switches on kind, constructs a fresh instance, copies every field, and rewrites the target's own self-referential fields (a self-loop exit) in the same pass — no redundant load of the about-to-be-deleted `oldId` file. `Referrers(kind, oldId)` naturally includes the target's own self-reference; the external cascade loop explicitly excludes it (matching `ReferrerKind == kind && ReferrerBlueprintId == oldId`) to avoid double-writing against a stale file.
- **Choose-at-creation and post-hoc rename share one id-validation rule, and one create-guard.** `ValidateBlueprintId` (non-empty, filename-safe `[A-Za-z0-9._-]+`, no `..`, reserved-device-name check, soft kind-prefix warning) backs both `RenameAsync` and the new `CreateAsync` create-guard. `CreateAsync` is a dedicated guarded write (`ValidateBlueprintId` + `Resolves` uniqueness refusal, delegating to `SaveAsync`) — edits stay on the unguarded `SaveAsync` (overwrite-on-edit, contract unchanged); `CreateNew(kind, name, string? blueprintId)` falls back to the existing adhoc generator when the id is blank.
- **YAML-only boundary preserved (INV-22/23).** Rename never opens SQLite or mutates the live world. `LocationComponent.RoomBlueprintId` (persistent player/item state) and `World:StartingRoomBlueprintId` (config) are warned, not rewritten; the live world re-keys on the next `reload`; a player saved in a renamed room falls back to the starting room via the existing `CharacterHydrationHandler` recovery. The reach-into-persistence alternative is deferred — see Follow-ups.
- **The cascade stays best-effort / non-transactional, matching delete.** A mid-rename failure can leave a partially-rewritten set, recoverable via `SweepBroken`. Folded into the existing *Atomic multi-file content cascade* backlog item rather than building a transactional multi-file writer disproportionate to this slice.
- **`StartRename` starts the new-id field blank, not pre-filled with the current id (deviation caught in manual verification).** The original implementation pre-filled the rename input with `BlueprintId` so the author could edit from the current value; a browser smoke test showed that clicking into the field without first clearing it (the default browser behavior — a click positions the caret, it does not select-all) and typing produces an accidental `oldId + newId` concatenation sent to `RenameAsync`. Fixed by starting the field empty, matching the plan's Main-flow framing ("entering `newId`") and removing the footgun for a real author hitting the same click-then-type sequence.
