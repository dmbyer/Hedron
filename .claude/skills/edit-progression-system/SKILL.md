# Edit the Progression System

Experience-driven progression (gameplay-model [Spine E](../../../docs/design/gameplay-model.md#spine-e--progression-experience-driven-growth--objectives)): every advanceable score has a per-track experience that accrues **through use**, and on crossing its next **cumulative threshold** grants a **linear** power step — each step costs a flat XP increment and the power step is linear, so power is near-unlimited; the *rate* of gain slows through the use rows' chance decay and through anti-grind (challenge gating) as the earner outgrows its opponents. That power is folded into effective scores **on read** through a contributor port — never baked into base, never cached.

This skill is how you **extend or tune** that system: add an XP source, adjust the curves, add a track, or generalize triggers to a data table.

> **Status.** Documents the as-built pattern through slice `prog-6` (durable design: [`docs/features/progression/progression.md`](../../../docs/features/progression/progression.md) · [`progression-system.md`](../../../docs/features/progression/progression-system.md); as-built history: [`docs/roadmap/completed/progression-substrate.md`](../../../docs/roadmap/completed/progression-substrate.md) · [`progression-use-based-xp.md`](../../../docs/roadmap/completed/progression-use-based-xp.md)). Symbol names (`IProgressionSystem`, `ProgressionTrack`, `XpSource`, `AdvancementRule`, `IAdvancementRuleRegistry`, `ProgressionConstants`, `ProgressionEffectContributor`) match the shipped code.
>
> **Layer 3 has already landed.** The third XP source arrived in `prog-6`, so the bespoke-handler-per-source pattern is *gone*: one `AdvancementHandler` reads `ProgressionConstants.Rules` through `IAdvancementRuleRegistry`. **Adding an XP source is now adding a row, not adding a handler.**

**Authoritative:** [progression-system.md](../../../docs/features/progression/progression-system.md) · [balance catalog](../../../docs/design/balance.md) (knob homes + maintenance contract) · [checklist](../../../docs/architecture/checklist.md) (INV-24 contribute-on-read, INV-5/INV-8 return-vs-publish, INV-19 framework-at-3, INV-26 determinism) · [config Category 3](../../../docs/architecture/05-configuration.md) (balance constants).

## The three layers (how progression is extended)

1. ~~**Mechanism = a handler on a game event.**~~ **Superseded at `prog-6`.** This was the layer-1 shape while sources were few; the third source triggered the layer-3 promotion, and there is now exactly **one** handler (`AdvancementHandler`) subscribed to every trigger event. A new source adds a subscription line to that handler (mechanical field mapping only) plus a rule row — never a new handler.
2. **Tuning = data (many), in `ProgressionConstants` now → YAML later.** Which track a source feeds, base amount, anti-grind, threshold curve — named constants, changed in the same commit; promote to YAML (Category 2, OD-2) only when recompile-free / per-mob / per-area tuning is a real need.
3. **Generalization = an advancement-rule table (Spine F) — ✅ shipped at `prog-6`.** `ProgressionConstants.Rules` holds one `AdvancementRule` per `XpSource`, read through `IAdvancementRuleRegistry`; `AdvancementHandler` is the one thin handler over all of it. A row carries its candidate tracks, its `AdvancementEligibility`, its base range, its `BaseChance`/`ChanceDecayPerImprovement`, and its `SourceScale`. Rows are compiled (Category 3); YAML at OD-2, and note the promotion is gated on reworking the CI-pinning contract, not on inertia.

## Recipe: add a new XP source (= add a rule row)

**Do not add a handler.** The rule table exists; this is a row plus a mapping.

1. **Find or add the event.** Use the past-tense event for the action (`CraftCompletedEvent`, `ObjectiveCompletedEvent`, item `read`, …). If none exists, the action's Initiator/handler publishes it — a **system never does** (INV-5). See [add-event](../add-event/SKILL.md).
2. **Add an `XpSource` enum value** — the stable key for the source and the rule table's key.
3. **Add an `AdvancementRule` row to `ProgressionConstants.Rules`**: candidate `StaticTracks`, `IncludesSubjectTrack`, the `AdvancementEligibility` the source needs, `BaseAwardMin`/`Max`, `BaseChance`, `ChanceDecayPerImprovement`, `SourceScale`.
4. **Add the trigger to `AdvancementHandler`**: implement `IEventHandler<TEvent>`, map the event's fields into a `UseAwardContext`, call `AwardUseExperience`, and route the result through the existing `PublishAsync` helper. **Mechanical mapping only** (plus, if the trigger names an opponent, one `IRelativePowerSystem.Relate(earner, opponent).Ratio` read into `OpponentPowerRatio`) — every discard condition belongs in the rule's `AdvancementEligibility`, evaluated at the system tier (INV-8). If you catch yourself writing `if (@event.Something == 0) return;` in the handler, that is an eligibility flag you have not added yet.
5. **Subscribe it** in `Server/Program.cs` alongside the existing `AdvancementHandler` subscriptions.
6. **Mind the draw contract (INV-26).** A rule whose effective chance is `>= 1.0` must short-circuit without an `IRandom` call, and an ineligible candidate must consume **zero** draws — the balance sandbox shares one seeded stream, so an extra draw moves every pinned golden. `ProgressionSystem.RollAward` already implements this; do not add an unconditional roll anywhere.
7. **Consider whether the source grants power.** A row whose candidate tracks are `ScoreId` tracks adds a *continuous new source of attribute power* that the `progressionRate` sim currently cannot see. Say so in the plan, set conservative defaults, and check the balance doc's Known gaps.
8. **Tests** ([add-tests](../add-tests/SKILL.md)): Tier-1 for the rule's eligibility + chance/scale math and its **draw sequence**; Tier-2 for the handler's field mapping and event fan-out; extend the Tier-3 flow if it's a headline source.

## Recipe: tune progression

- `PowerPerImprovement` (linear step), the threshold curve, base awards, and the anti-grind floor/cap ratio thresholds all live in `ProgressionConstants` ([Category 3](../../../docs/architecture/05-configuration.md)); the *power* that ratio is computed from is **effective** power measured by `IRelativePowerSystem` through `IStatSystem` and the oracle's `PowerBudgetTunables.Weights` — an injected plain-data record (`PowerBudgetSystem`'s single constructor parameter), composed by the host from the balance-standards registry (`IBalanceStandardsRegistry`, sim-1) or its compiled `Default` fallback, not a static constants class. **The per-step XP cost is flat:** the *cumulative* threshold grows (`ThresholdBase + n × ThresholdIncrement`), but each step costs the same `ThresholdIncrement`. What slows gain per action is the use rows' **chance decay** and, on opponent-bearing triggers, **anti-grind** as the earner outgrows its opponents. The power step stays **linear** — don't curve the power to slow gains.
- Validate a tuning change at scale by running a `kind: progressionRate` scenario through the balance-simulator program's sim engine (sim-4 — `ProgressionScenarioExecutor` sweeps the real `AwardCombatExperience`/`TryImprove` seam via `dotnet run --project Server -- simulate` or the Simulation editor page), not by hand.
- **`GlobalXpScalar` is the macro knob** (`prog-6`): it multiplies every award from every source inside the system, so no call site can bypass it. Reach for it to move overall pacing; reach for a rule row's `SourceScale`, an ability's `XpScale`, or a mob's `XpScale` to move one thing.
- **The chance curve is the use rows' rate-slowing knob.** `BaseChance / (1 + improvements × ChanceDecayPerImprovement)` composes with the growing cumulative threshold and with anti-grind on the same track. Tune one at a time and know which you are moving — a change to several at once is very hard to read in a sweep.
- **`SimulationInvariantTests` CI-pins progression golden numbers** (kills-to-first-improvement at a fixed seed, milestone-gap monotonicity) at the compiled `ProgressionConstants` values — a deliberate tuning change to `ThresholdBase`/`ThresholdIncrement`/`GlobalXpScalar`/the `CombatKill` row's `BaseAwardMin`/`BaseAwardMax`/`AntiGrindFloorRatio` must re-pin those tests **in the same commit** (the sim-2 regression-pin posture, same as the combat win-rate pins). Note the sweep still models kill events only — a change to the `AbilityUse` or `DamageTaken` rows (including their anti-grind, applied when an opponent is named) will **not** move a golden, which is a blind spot, not a green light ([backlog](../../../docs/roadmap/backlog.md)).
- Need recompile-free / per-mob / per-area tuning? Promote those constants to YAML content (OD-2) — don't scatter `IConfiguration` reads.

## Recipe: add a track

- **A track is a `ProgressionTrack`** — one vocabulary, two shapes: `ProgressionTrack.Of(ScoreId)` for a score track and `ProgressionTrack.Ability(id)` for an ability track. A score becomes a track simply by being awarded to; nothing else to register.
- **Do not track derived scores** (`AttackPower`/`Defense`) — they rise via their inputs; tracking them double-counts.
- **Governed pools** (`Mana`/`Stamina`/`Astra`) grow via their governing attribute's track — don't give them an independent track without deciding the pool-derivation math.
- **Ability tracks are display-only** (`prog-6`). They share the engine, the component, and the threshold curve, but `ProgressionEffectContributor` folds only score tracks, so rank contributes **zero** power. An architecture-guard test pins this. Making rank scale potency or cost is a deliberate balance slice that must fold into [`power-model.md`](../../../docs/design/power-model.md) and re-pin goldens — not a drive-by change.
- **A new *kind* of track** (something that is neither a score nor an ability) widens `ProgressionTrack` with a third case and a third key prefix — it does **not** get a second improvement engine or a second XP store.

## Recipe: promote to the advancement-rule table (≥3 sources)

When 3+ XP sources exist, collapse the bespoke handlers into **one** thin advancement handler reading a registry: `XpSource/event → (track(s), amount formula, anti-grind, conditions)`. Hardcoded rows first (Spine F registry shape), YAML rows at OD-2. This is the [INV-19](../../../docs/architecture/checklist.md) "framework at the 3rd repetition" promotion — the `XpSource` key makes it additive, not a rewrite.

## Guardrails

- **Contribute-on-read, not base-mutation.** Progression power is pulled through the `IEffectContributor` port on read; **never** write it into a stored component and never cache it (INV-24). Discrete *permanent* growth (rare-material consumption → +base forever) is a **separate** direct-base-mutation action — different seam, don't conflate.
- **Systems return, handlers publish** (INV-5/INV-8). No `IEventBus` inside `ProgressionSystem`.
- **Pool reads are computed values too.** `IAttributeSystem`'s pool reads (`GetCurrent*`, `GetEffectiveMax`) are clamped to the effective cap, which folds every contributor — so a contributor's backing system must not read them any more than it reads `IStatSystem` (it would close the same cycle through `IEffectSystem`). Read raw component data, or take the value from the caller.
- **Eligibility is rule data, not a handler branch.** `AdvancementEligibility` (`RequiresAttributableActor`, `RequiresPlayerEarner`, `RequiresPositiveMagnitude`, `AppliesAntiGrindPowerRatio`) is evaluated inside `ProgressionSystem`. `AdvancementHandler`'s job is field mapping *event fields → `UseAwardContext`* plus one relative-power read per opponent-bearing trigger (kill → victim; offensive ability use → target; damage taken → attacker); opponent selection maps event facts, never a game-rule branch.
- **The RNG draw contract is load-bearing (INV-26).** A certainty short-circuits without a draw; an ineligible candidate consumes zero draws. `SandboxWorld` shares **one** seeded `IRandom` across every system in a run, so one extra draw shifts the whole stream and moves every pinned golden. Assert draw *sequences* directly with a counting fake `IRandom` — "the goldens didn't move" is a consequence to check, not the proof.
- **Don't fork the vocabulary.** Track key = `ProgressionTrack` — **one** engine, **one** component, **one** threshold curve, **one** `XpSource` vocabulary. The rule this states is *one track vocabulary*, not *one CLR type*: widening the key to cover ability tracks satisfies it, while a second XP store inside `Core/Modules/Abilities/` would be the literal second improvement engine it forbids. No parallel `TrackId` enum, and no per-feature XP dictionary.
- **Balance numbers live in constants** (Category 3), not `appsettings.json`, not the handler body.
- **The character-wide Tier baseline** (`AscensionEffectContributor`, shipped slice `prog-2`) is a *second* contribution on the same contribute-on-read seam — additive; don't rebuild the contributor to add it. `AscensionConstants.TierBaselineStep × IAscensionSystem.GetTier(entity)` folds alongside `ProgressionEffectContributor` with zero interface change to `IStatSystem`/`EffectSystem`.
- **`ProgressionSystem` never reads `IStatSystem`/`IEffectSystem` — the ratio is supplied by the caller.** `ProgressionEffectContributor` is a registrant *on* `IEffectSystem`'s contributor list; if `ProgressionSystem` itself called `IStatSystem.Get` (which folds that same contributor list), it would close a DI cycle back through its own contributor. So computed inputs (the anti-grind opponent ratio) arrive as **parameters**, gathered at the orchestration boundary. This generalizes to any future `IEffectContributor`: a contributor's backing system may consume raw component data or caller-supplied values, but never read a computed value from the seam it feeds. An architecture-guard test forbids `IStatSystem`, `IEffectSystem`, `IRelativePowerSystem` and `IPowerBudgetSystem` on `ProgressionSystem`. Discovered while wiring `prog-1` — see [`progression-system.md`](../../../docs/features/progression/progression-system.md#anti-grind-ratio-is-supplied-by-the-caller). **Confirmed a second time in `prog-2`:** `AscensionSystem` reads only raw `AscensionComponent.Tier` via `EntityService`, never `IStatSystem`/`IEffectSystem` — the same guardrail, now with two independent precedents (Progression, Ascension).
- **The anti-grind ratio is gathered through `IRelativePowerSystem`, at the handler and the executor.** `AdvancementHandler` (live) and `ProgressionScenarioExecutor` (sandbox, once per kill) call `IRelativePowerSystem.Relate(earner, opponent).Ratio` — effective power on both sides through `IStatSystem` and the core oracle — and pass it to `AwardCombatExperience(killer, victim, ratio)` or `UseAwardContext.OpponentPowerRatio`. `null` means no opponent (no ratio, draws unchanged); an unreadable opponent arrives as `0.0` and is ineligible, never ratio-free XP. A new opponent-bearing source flags `AppliesAntiGrindPowerRatio` on its rule and gathers the same way; a live-vs-sandbox parity test pins the two callers. The *trivial* label boundary **is** `AntiGrindFloorRatio` — never add a second constant for it. See [`relative-power-system.md`](../../../docs/features/progression/relative-power-system.md).
